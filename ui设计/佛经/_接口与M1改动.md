> 2026-10-22。项目按你现有的 `book_info` / `book_text_content` / `book_reach_record` 三张表来，没有用我早先另设计的 `sutra_*`。

---

## 一、数据库只加列，没建新表

### `book_reach_record` 新增 8 列

| 列 | 类型 | 说明 |
|---|---|---|
| `lastReadSeq` | INT UNSIGNED | 最后阅读章节 seq，0 = 没读过 |
| `lastReadOffset` | INT UNSIGNED | 阅读位置：**章内字符偏移** |
| `lastCopySeq` | INT UNSIGNED | 最后抄写章节 seq |
| `lastCopyOffset` | INT UNSIGNED | 抄写位置：章内字符偏移 |
| `copiedChars` | BIGINT UNSIGNED | 累计抄写字数（含重复抄写，只增） |
| `skippedChars` | INT UNSIGNED | 累计跳过格数 |
| `readDate` | DATETIME NULL | 最后阅读时间 |
| `copyDate` | DATETIME NULL | 最后抄写时间 |

原来的 `readPercent` / `copyPercent` 保留不动，详情页和列表页继续用，不用改。

### `book_text_content` 加了索引

```sql
ALTER TABLE book_text_content ADD KEY idx_book_seq (bookId, seq);
```

原来只有主键，`WHERE bookId=? AND seq=?` 是全表扫。3870 行时看不出差别，扩经目后就是硬伤。

### 为什么不用新表

读经和抄经是两种语义（单值覆盖 vs 累加），但**都是「一人一部经一行」**，共用 `(accountId, bookId)` 唯一键天然成立；拆表只会让书架列表多一次 join。会话流水（时长、字数明细）等 M4 真要做统计时再单独建 `book_copy_session`，现在不预建。

### 百分比与位置的关系（容易误解，特别说明）

- `readPercent` = **读到过的最远处**，只增不减。回看第一章不会把进度打回 3%。
- `lastReadSeq/Offset` = **上次停在哪**，直接覆盖。回看后下次进来就续在回看处。

两者语义不同，不要求时刻一致。抄经同理，但 `copyPercent` 用当前章位置算，`copiedChars` 独立累加。

## 二、5 个接口

全部挂在 `BookController`，`session` 照旧走 query 参数，风格与现有接口一致。

### 1. 目录

```
GET /book/getBookChapterList?session=xxx&bookId=1
```

返回 `R<List<BookChapterItem>>`：

```json
{
  "code": 0, "msg": "成功",
  "data": [
    {
      "seq": 1, "juanNo": 1, "juanTitle": "般若波罗蜜多心经",
      "sectionKind": "序", "sectionTitle": "大明太祖高皇帝御制般若心经序",
      "partNo": 1, "charCount": 770,
      "contentHash": "467b1bf12a9f5b37ec6d5c2d63c983eb"
    }
  ]
}
```

- 不含正文，《华严经》557 章约 75KB
- 服务端 Redis 缓存 24h，key `book_chapter_list:{bookId}`

### 2. 单章正文

```
GET /book/getBookChapter?session=xxx&bookId=1&seq=3&contentHash=本地指纹(选传)
```

返回 `R<BookChapter>`，含 `content`（简）、`contentTrad`（繁）、`prevSeq`、`nextSeq`。

**指纹一致时不下发正文**：

```json
{ "code": 0, "data": { "bookId": 1, "seq": 3, "charCount": 330,
  "contentHash": "abc...", "prevSeq": 2, "nextSeq": 0, "notModified": true } }
```

客户端看到 `notModified=true` 就继续用本地内容，不要拿空 content 覆盖缓存。

服务端 Redis 缓存 key `book_chapter:{bookId}:{seq}`，24h。

### 3. 查进度

```
GET /book/getBookProgress?session=xxx&bookId=1
```

```json
{ "code": 0, "data": {
  "bookId": 1, "readPercent": 26, "copyPercent": 16,
  "lastReadSeq": 3, "lastReadOffset": 100,
  "lastCopySeq": 3, "lastCopyOffset": 200,
  "copiedChars": 150, "skippedChars": 2,
  "totalChars": 1233, "isInShelf": false
} }
```

没有记录时返回全 0 对象，`totalChars` 仍然有值（来自 `book_info.charCount`），客户端不用判空。

### 4. 上报读经进度

```
POST /book/updateReadProgress?session=xxx
Content-Type: application/json

{ "bookId": 1, "seq": 3, "charOffset": 100 }
```

返回更新后的 `BookProgress`，客户端可以直接刷新详情页文案。

`charOffset` 是**章内字符偏移**（`content` 的字符串下标），服务端会截断到 `charCount` 以内防越界。

### 5. 上报抄经进度

```
POST /book/updateCopyProgress?session=xxx

{ "bookId": 1, "seq": 3, "charOffset": 200,
  "chars": 50, "durationMs": 30000, "skippedChars": 0 }
```

- `chars` 是**本次净增**，服务端做 `copiedChars = copiedChars + chars`
- `skippedChars` 同样按增量累加
- 返回更新后的 `BookProgress`

### 数据流（只按这个走，别在 UI 里直接吃网络回调）

```
打开阅读页
 ├─ Room 有目录 → 先渲染（秒开）
 ├─ 请求 /getBookChapterList → 落 Room → 若数据有变再刷新
 ├─ 请求 /getBookProgress → lastReadSeq → 定位到该章
 └─ 当前页 + 下一章
      ├─ Room 有 → 先显示 → 带 contentHash 问服务端
      │              └─ notModified=true → 不动
      │              └─ 有更新 → 落 Room + 刷新该页
      └─ Room 没有 → 请求 → 落 Room → 渲染
```

## 七、实测结果（2026-10-22，本地起服务打真接口）

服务端 `mvn package` 打成 jar 起在 8899，数据库/Redis 用的就是线上那套。

| 用例 | 结果 |
|---|---|
| 目录 bookId=1 | 3 章，字段齐，hash 正确 |
| 正文 seq=3 | `prevSeq=2`、`nextSeq=0`、330 字，简繁都有 |
| 带本地 hash 再请求 | `notModified=true`，`content` 为空（符合预期） |
| seq=1 边界 | `prevSeq=0`，`nextSeq=2` |
| seq=999 | `code=-37 章节不存在` |
| 查进度（无记录） | `totalChars=1233`，其余全是 0，不返回 null |
| 读进度 seq=3/offset=100 | `readPercent=81`（(903+100)/1233） |
| 回看 seq=1/offset=50 | `readPercent` 保持 81，`lastReadSeq` 变 1 |
| 抄进度 50 字 → 60 字 | `copiedChars` 50→110，`skippedChars` 0→2，百分比 89→94 |
| 非法参数 bookId=0 / seq=0 | `-9527 傻逼滚粗`（沿用项目既有风格） |
| 目录缓存 | 华严 557 章：首次 268ms → Redis 命中 72ms |

### 实测发现并修掉的两个问题

1. **`isInShelf` 被 Jackson 输出成 `inShelf`**。Lombok 对 `boolean isInShelf` 生成 `isInShelf()`，Jackson 剥掉 `is` 前缀。客户端字段是 `isInShelf`，会解析不到。已按 `BookInfo` 里的老写法加 `@Getter(onMethod_ = {@JsonProperty("isInShelf")})`。
2. **`seq` 越界返回的是「书籍不存在」**。加了 `CHAPTER_NOT_FOUND = -37`，三个方法统一改掉。

测试用的那个账号（32359249）原有 `readPercent=22 / copyPercent=22`，测试写入后已恢复原值，新列全部清零。
