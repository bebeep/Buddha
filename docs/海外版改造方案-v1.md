### 1.2 首页重设计：修行仪表盘 + 内容流

不再沿用旧首页布局（金刚区 6 宫格 + banner）。新版自上而下 6 个区块：

1. **佛历头卡**：佛历年份 / 今日节日 / 斋日 / 宜忌（`TodayBuddhaInfo` 接口现成）。**整卡可点 → 直接进签到日历页**（`SignInFragment`，月历+佛历节日一体，现成页面）；签到弹窗逻辑保留在日历页内。日活锚点
2. **今日修持卡**：日常行为打卡格，**槽位服务端可配置**（显示什么行为、跳哪个页面、进度来源），不强绑任何概念。默认三格：**早课**（引导式晨间修持，见九）/ **诵经**（`FojingReadFragment`）/ **抄经**（`FojingCopyFragment`）。后台下发 config：`[{title,icon,target,progressApi}]`
3. **金刚区（4 宫格）**：佛经 / 许愿树 / 寺庙 / **念佛计数**——纯功能入口。变现与游戏功能不上金刚区。注：原计划的祭怀模块经风险评估移出，由念佛计数替代（见八）
4. **供灯状态条**：「我的长明灯还剩 N 小时 · 去续燃」——跨 tab 引流到拜佛页，灯将熄时自然产生 IAP 续燃转化；无灯时显示「点一盏灯」引导首购
5. **游戏卡（3 卡横排）**：禅院 / 放生 / 禅值商店（钱包余额 + 兑换入口）。游戏入口全部收拢在这里，不再占 tab
6. **佛友圈精选**：推荐算法/运营精选的动态流（复用 MomentAdapter），下滑无限刷，点击进佛友圈 tab

布局实现建议：外层 RecyclerView 多 itemType（或 ConstraintLayout + 内嵌小 RV），不要 ScrollView 套 RV。

### 1.3 拜佛 Tab：3D 佛龛场景（供灯并入）

原 WorshipFragment 只有佛像 3D。升级为一个完整佛龛场景：

- **同屏元素**：佛像（buddha_01.glb）+ 灯位（灯具 glb，1~N 盏）+ 香炉（可选）
- **交互**：触摸旋转整场景；点灯 / 续燃 / 上香按钮在底部；换佛龛场景（skybox）与灯具（商城装扮）入口在右上
- **供灯不再是独立页面**：原方案 LampFragment 取消，供灯逻辑（IAP、灯油时长、灯火状态）全部挂在拜佛 tab
- 复用：Sceneform-EQR 加载链路、`buddhaConfig` 配置机制（扩展为 `shrineConfig`：佛像+灯位+场景组合）、eq-renderer 自带 skybox/IBL
- 商城装扮挂载点：佛龛背景（shrine_scene）= 换环境贴图；灯具外观（lamp_skin）= 换灯位 glb

## 三、供灯（核心变现，替代功德捐赠）

### 3.1 形态
- **供灯并入拜佛 tab 的 3D 佛龛场景**（见 1.3），不做独立页面
- 玩法拆两层：
  - **消耗品（IAP consumable）**：灯油/酥油——点燃限时灯（1天/7天/30天），烧完可续
  - **非消耗品（IAP non-consumable）**：灯具外观永久买断（见商城）
- 灯火长明榜概念**不要**做（排行榜已砍，且付费排名是合规雷区），改做「我的灯位」个人展示 + 分享
- 首页「供灯状态条」负责召回与转化（见 1.2 第 4 区块）

### 3.2 3D 实现直接复用现有引擎
- WorshipFragment 已有 Sceneform-EQR 完整用法（sceneLayout.init / ModelRenderable / 触摸旋转 / 自动旋转），抄这套
- 佛龛场景 = `eq-renderer/src/main/assets/enviroments/` 已内置 skybox/IBL（pillars_2k_skybox.ktx 等），换环境贴图即换场景
- 灯具外观 = 不同 glb 模型（tripo01/02.glb 生成管线现成）
- 服务端 `buddhaConfig` 机制照搬：新增 `lampConfig`（灯具列表 + 模型 URL + 价格 SKU id）

### 3.3 支付（唯一合规出口）
- Android：Google Play Billing Library；iOS：StoreKit 2
- **消耗品/非消耗品要分开声明**，服务端必须验证 purchase token / receipt 后再发货
- 全 App（含 H5 游戏内）不得出现任何外链支付/引导——Apple 3.1.1、Google Payments 政策红线

### 5.2 游戏与主 App 的经济打通

## 八、祭怀模块：风险评估与替换方案

### 8.1 为什么搁置祭怀
- **数据敏感**：逝者姓名/照片/生卒属敏感个人信息，海外多国隐私法（新加坡/泰国 PDPA、印尼 PDP）对逝者数据处理规则各不相同，合规成本高
- **UGC 风险最高的一类**：纪念页可被用于骚扰（给活人"建坟"）、诅咒、恶搞，双端审核都会重点盯，举报处理成本高
- **市场敏感**：马来西亚/印尼（穆斯林为主）对丧葬纪念类内容的宗教敏感度高；华人市场内清明/中元民俗差异也大
- **与变现主链路无关**：投入产出比不如把人力给早课和禅院

### 8.2 替代方案：念佛计数（金刚区第 4 格）

选它的理由：**零 UGC、零敏感数据、高频工具型、开发成本极低、与早课/禅院共用禅值账户**。

- 一期形态：佛号/短咒计数器（预置佛号池：阿弥陀佛/观音圣号/六字大明咒等，服务端可配）
- 交互：大按钮点击/摇一摇计数，今日数 / 累计数 / 连续天数；可选禅修计时模式（倒计时静坐）
- 数据：`PracticeRecord`（type/count/duration/date）服务端记账，进禅值账户——**与早课、游戏结算同一账户**，形成"修行为主、游戏为辅"的统一经济
- 二期可扩展：日课目标（每日 108 声）、完成提醒
- 代码落点：新 `fragment/practice/CounterFragment.kt` + `CounterVM`，纯本地计数 + 定时批量上报，无审核负担

## 九、早课模块详设（拉日活核心）

### 9.1 定位
每天一次、3~5 分钟的**引导式晨间修持流程**。它不是页面，是一条"步骤流"——把 App 里已有的动作（拜佛、诵经、发愿）串成一条固定路径，完成即打卡。

### 9.2 流程（五步）

| 步骤 | 内容 | 实现复用 |
|---|---|---|
| 1 · 礼佛 | 3D 佛龛场景起手，合十/点击拜三拜 | 直接复用拜佛 tab 的 SceneLayout 与 glb 链路 |
| 2 · 诵经 | 预置短经池选一篇（心经 260 字 / 大悲咒节选 / 普门品节选，服务端可配），静读计时 | 复用佛经阅读的内容源与排版组件 |
| 3 · 称念 | 念佛计数：跟读佛号 21 声 / 108 声 | 复用念佛计数模块（见 8.2） |
| 4 · 发愿 | 今日一愿，一句话（一期纯本地保存，不上传 = 零审核成本） | 新写，最简 |
| 5 · 回向 | 完成页：连续天数 + 今日禅值 + 回向文 + 分享卡 | 新写；分享卡模板化生成 |

### 9.3 打卡与奖励
- **时段**：按用户本地时区 4:00–12:00 记为"早课"，其余时段完成记"晚课"（同一流程，文案换）——海外用户跨时区直接解决
- **连续天数**：里程碑 7 / 21 / 49 / 108 天，奖励**虚拟物品**（限定头像框、灯具外观）——全部免费可得，IAP 卖的是另外的普通外观，不搞付费墙
- **禅值**：每天早课固定产出少量禅值，与游戏产出同账户
- **防作弊**：诵经步骤有时长下限校验（例如心经 ≥40 秒），服务端结算
- **提醒**：FCM / APNs 本地时区晨间提醒，用户主动开启才发

### 9.4 合规红线
- 文案**不承诺现实福报回报**（"念了就有好运"这类话术商店审核和宗教合规都忌讳），用"修持记录"口径
- 无任何付费环节，奖励全虚拟
- 发愿文本一期不出设备，零 UGC 负担

### 9.5 代码落点
- 新 `fragment/practice/EarlyPracticeFragment.kt`（步骤流状态机）+ `EarlyPracticeVM`
- 复用：WorshipFragment 3D 链路、佛经内容源、念佛计数、禅值账户、MainVM 的 TodayBuddhaInfo（判断今日节日给特殊早课文案）
- 首页入口：今日修持卡第一格 + 卡片头部"开始早课"主按钮

## 十、首页详设（定稿）

### 10.1 区块总表

| # | 区块 | 数据源 / 接口 | 状态 | 点击行为 |
|---|---|---|---|---|
| 1 | 佛历头卡 | `TodayBuddhaInfo`（已有）+ 本地公历兜底（已写 localDateText） | 加载中先铺本地；接口失败静默保留兜底 | 整卡 → SignInFragment（日历页）；右上"签到"胶囊同目标 |

| 4 | 金刚区 | 本地静态（图标后端可配可选） | 无网络态 | 佛经→BuddhaTextsFragment；许愿树→WishTreeFragment；寺庙→TempleListFragment；念佛→CounterFragment |

### 10.2 排序逻辑（为什么这么排）

日活锚（1–2）→ 转化（3）→ 导航（4）→ 时长（5–6）。

- 首屏（折叠线以上）保证区块 1–4 全部露出：**签到、早课、供灯、四大功能零滑动可达**——变现钩子和日活钩子都在第一屏，这是整页设计的硬约束
- 游戏卡和精选流放折叠线下：它们的价值在"往下滑"的用户身上，不与转化位抢首屏
- 供灯条放在修持卡之下、金刚区之上：用户每天完成打卡后视线自然下移，此时灯的状态（尤其将熄态）刚好接住，转化路径最短

### 10.3 实现方案

- **单 RecyclerView + 多 viewType**（6 种 viewType），不要 ScrollView 套 RV
- 骨架屏：进页前 1–5 区块按占位高度出 skeleton，feed 区单独分页加载
- 下拉刷新：整页下拉只刷新 1–5 区块的聚合接口 + feed 第一页
- 跨区块联动：早课完成 / 续燃成功 / 签到成功后回首页，EventBus（MessageEvent 已有）通知刷新对应区块，**不要整页刷新**
- 数据聚合：新增 `home/summary` 聚合接口一次拉回（修持进度 + 灯状态 + 禅值余额 + 连续天数），避免首屏 4 个并发请求在弱网下互相等待

### 10.4 埋点（提审后优化的依据）

每区块曝光 `home_block_view_{n}` + 点击 `home_block_click_{n}`，供灯条三种状态分别埋点——上线两周后按转化数据调整区块顺序，配置化预留：区块顺序由后端 config 下发，支持不发包调序。

## 十一、寺庙模块：海外数据方案

### 11.1 问题
现行模式 = 后台人工录入（`getTempleList` 全量返回，字段 name/images/intro/history/addr/lat/lng）。国内寺庙自己熟好录，海外没有录入渠道，全人工不现实。

### 11.2 数据源对比

| 来源 | 质量 | 成本 | 限制 |
|---|---|---|---|
| **OpenStreetMap**（amenity=place_of_worship + religion=buddhist） | 中：位置准、名称多语言，无介绍无照片 | 低：Overpass API 免费批量拉 | ODbL 协议，需署名页 |
| **Wikidata/Wikipedia** | 中：寺庙条目有坐标+多语言简介，Commons 有 CC 图片 | 低：SPARQL 一次批量导 | 条目覆盖不均（泰国/台湾/日本好，欧美差） |
| **Google Places API** | 高：营业状态/照片/评分全 | 高：按次收费 | **ToS 禁止长期落库**，只能运行时按需查询+短缓存 |
| **佛教组织公开名录** | 极高：佛光山/慈济/法鼓山海外道场、各国佛教会官网 | 中：人工整理 | 慢，覆盖大庙不全 |
| **用户共建（UGC）** | 递增 | 前期低后期审核重 | 假寺庙/骗局风险，需审核闭环 |

### 11.3 分期落法

**一期（冷启动，零数据负担）："附近寺庙"按需查询 + 精选库**
- 新增"附近"查询：App 端传经纬度 → 后端调 OSM Overpass 实时查半径内佛教场所 → 返回精简列表（名称/坐标/距离），点进详情再补 Wikidata 简介。**不落库，零采集成本，开服即有全球数据**
- 同时人工精修 50–100 条"精选寺庙"（华人密度高的城市优先：新马泰/港澳台/北美/澳洲/日本），走现有 `getTempleList` 通道，信息走人工+佛教组织名录，宁缺毋滥
- 列表页双 tab：「精选」(人工库) /「附近」(实时查询)

**二期：Wikidata 批量扩充**
- SPARQL 导出全球佛教寺庙 → 清洗去重（OSM+Wikidata 坐标对齐）→ 进库做基础档案（名称多语言/坐标/一句话简介/Commons 图片）
- 基础档案不带评论/推荐，只有精选庙和被用户互动过的庙进入"完整页"

**三期：开放共建（谨慎）**
- 用户提交/纠错寺庙 → 后台审核队列（AuditController 扩展）
- 寺庙认证（claim）：上传当地宗教团体登记证明后可自维护法会/活动信息——各国登记形式不同，做之前单独立项评估
- 法会/活动信息是真正的留存价值点，但只认证后才开

### 11.4 合规注意
- **OSM 数据页加署名**（ODbL 要求），设"地图数据来源"说明
- **Google Places 不用**（费用 + ToS 落库限制），全链路用 OSM/Wikidata
- 照片只用 Commons CC 或后台自传，不爬官网图
- 寺庙页维持无功德箱/无募捐链接的既定红线；认证寺庙也不得在 App 内收款
- 「附近」查询要用户授权定位，隐私政策列明"仅用于计算距离，不存储轨迹"

### 11.5 字段扩展（TempleBean / temple 表）
新增：`region`（国家/城市索引）、`langNames`（多语言名 JSON）、`source`（curated/osm/wikidata/user）、`verified`（认证标记）、`services`（法会活动，三期）。现有 recommend/comment 机制保留，仅对精选庙开放。

## 十五、UGC 合规件与收藏（2026-11-02 第三批，已完成）

Apple 1.2 与 Google UGC 政策对"用户能发内容"的产品有四项硬要求：**举报、拉黑、内容过滤、可联系的开发者**。项目原有 `IAuditService`（阿里云内容安全）已覆盖动态/评论/图片/视频的过滤，缺的是举报与拉黑的可达入口，以及拉黑生效后的服务端过滤。

### 15.1 举报

- 后端：`account/report` → `report_record`（原有表），`reportType` 1动态 2评论 3用户，`reportTag` 取 `spam/porn/abuse/fraud/other`
- 客户端：`ReportDialog`（五项原因，单选 + 提交），动态详情右上角菜单、他人主页菜单均可触发
- **`fraud`（假借宗教名义诈骗收费）单独成项**：东南亚市场冒充法师收费是高发问题，后台按 tag 筛出来能快速处置

### 15.2 拉黑

|---|---|

## 十六、登录换轨 / 通知 / 内购（2026-11-02 第四批，已完成）

这一批把三件上线前必须落地的事一起做了：账号体系换成海外版、通知接 OneSignal、支付走双端内购。

### 16.1 登录换轨：手机号整体下线

**删除的**
- 手机号 + 密码登录（`account/login` 的旧语义）
- 微信/支付宝充值：`getPayConfig`、`rechargeByWx`、`rechargeByAli`（海外不做第三方钱包，虚拟商品必须走 IAP，否则违反 App Store 3.1.1）
- 空壳桩接口：`sendVerifyCode`、`checkVerifyCode`、`bindAccount`、`modifyPassword`
- 客户端本机保存的明文密码（升级上来的机器会主动清掉）

**新增的**
| 接口 | 说明 |
|---|---|
| `POST /account/login` | 按 `loginType` 分发：1 邮箱密码 / 2 Google / 3 Apple |
| `POST /account/register` | 邮箱注册，成功直接下发 session（不用再登一次） |
| `GET /account/checkEmail` | 注册页边输边查重 |
| `POST /account/bindThird` | 已登录账号补绑 Google/Apple/邮箱 |
| `POST /account/setPassword` | 第三方注册的账号补一个密码 |
| `POST /account/refreshSession` | 冷启动自动登录（唯一的长期登录通道） |

**第三方凭证校验**（`ThirdAuthService`，零依赖实现）
- Google：走官方 `tokeninfo`，再核 `aud / iss / exp`。**aud 必须命中我们自己的 client id**，否则别人 App 的合法 idToken 也能登进来
- Apple：拉 JWKS 按 `kid` 取公钥，本地 RS256 验签，核 `iss / aud / exp`
- 两者都缺配置时**直接拒绝登录**，不会"配置漏了就跳过校验"

**账号关联策略**：Google/Apple 返回的邮箱若 `email_verified=true` 且该邮箱已用密码注册过，直接绑到那个账号。前提是邮箱已验证——否则等于允许用任意邮箱认领别人的账号。

**客户端**
- 登录页重做：Google（白底，符合品牌规范）+ 邮箱表单，登录/注册同屏切换
- Google 走 Credential Manager（`androidx.credentials`），老 `GoogleSignInClient` 已被 Google 废弃
- 未配置 client id 时 Google 按钮整块隐藏 —— 宁可少一个入口，不给点了必然失败的按钮
- 冷启动用 SP 里的 session 调 `refreshSession`，续不上才回登录页

**顺手修的账号体系隐患**
1. `account_info.phoneNum` 是 UNIQUE，海外版所有账号写空串 → **第二个用户注册必然唯一键冲突**。已降为普通索引
2. `registerDeviceUUID` 也是 UNIQUE → 同一台设备不能注册第二个账号（家人共用平板很常见）。已降为普通索引，`getAccountByDeviceUUID` 补 `LIMIT 1`
3. `email/googleId/appleId` 改为 `NULL + UNIQUE`：未绑定存 NULL（唯一索引容忍多行 NULL），绑定了就真唯一，防并发注册同邮箱
4. `tryPlay` 里 `new Random(999)` 固定种子 + `accountId` 还是 0 → **同一秒注册的两个游客会拿到同一个 session**。改用 UUID
5. `getAccountBySession` 里 `accountMap.get("phoneNum").toString()` 遇到 null 会 NPE。统一走 `str()` 兜底

### 16.2 通知：OneSignal

**服务端**
- 新表 `account_push_record`：一个账号可多设备（`subscriptionId` 唯一，`accountId` 不唯一）
- `OneSignalClient`：走 v2 接口 `/notifications` + `include_aliases.external_id`，**用 accountId 作为 external_id**，换机/重装/多设备都不用服务端维护映射
- `POST /push/register`、`/push/unregister`、`/push/switch`
- `PracticeRemindTask`：每小时按用户上报的时区判断"他的本地是不是 7 点"，只推当天没做早课的人

**客户端**
- `PushManager`：`init` 在 Application、`bind(accountId)` 在登录成功、`unbind()` 在退出/注销
- 权限申请放在**登录之后**，冷启动就弹被拒率明显更高
- 时区随订阅一起上报——早课提醒必须按用户本地时间，不是服务器时间
- 退出登录的顺序：**先调解绑接口、再 `OneSignal.logout()`**。反过来解绑请求会带已失效的 session 被拒，旧账号继续收推送

**为什么按小时轮询而不是给每人算执行时间**：用户分布在 UTC+7/+8 多个时区且会随时区漂移（留学、出差），一小时扫一遍、用每人上报的时区算本地时间，是这套逻辑里最不容易错的做法。

### 16.3 内购：双端验单

- `GooglePlayVerifier`：服务账号私钥签 RS256 JWT → 换 access_token（提前 5 分钟过期）→ `purchases.products.get`
- `AppleIapVerifier`：`verifyReceipt`，`status=21007` 自动切 sandbox 重试（审核期必然遇到）
- `iap.allow-mock` 默认 **false**：生产拒绝 `mock_` 前缀回执
- 商品 ID 复用 `shop_dress_config.iapProductId` 的 `android:xxx,ios:yyy` 格式

**验单结果分两类**（`IapVerifyResult.permanent`）
- 临时失败（网络、平台 5xx、未配置）→ 订单保持 0，用户可重试
- 永久失败（已退款、`purchaseState≠0`、交易不存在、伪造 token）→ 订单置 4，不再给重试

不分的话要么把正常用户卡死，要么给伪造回执留无限重试。

**客户端（`BillingManager`）**
- 接 BillingClient 7.x，`queryProductDetails` → `launchBillingFlow`
- **消耗型必须 consume**：灯油是消耗品，不 consume 用户第二次买不了同一件
- **永久型必须 acknowledge**：购买后 3 天不 acknowledge，Google 自动退款并把商品收回
- `setObfuscatedAccountId` 传账号混淆值，便于平台侧对账

**修掉的资损点**：原 `verifyAndDeliver` 里 `status >= 2 就返回 ok`，把「已退款(3)」「验单失败(4)」也当成功返回——用户以为买到了、库里却没有装扮。已改为精确匹配状态。

## 十七、佛历订阅提醒（2026-11-02 第五批，已完成）

拉日活最实在的一环：用户在节日收到一条不打扰的提醒，比任何弹窗都管用。这一批把提醒从"服务端能推"补到"用户能自己配"。

### 17.1 三种规则，一张表

`calendar_remind_config`（一行 = 一条规则），没有加新表：

| remindType | 含义 | 可配项 |
|---|---|---|
| 1 | 佛历节日（佛菩萨圣诞/成道/涅槃 + 盂兰盆、卫塞节） | 提前 0/1/2/3 天 + 时刻 |
| 2 | 斋日（农历初一、十五） | 时刻 |
| 3 | 每日自定义（用户自己写一句话） | 文案 + 时刻 |

补了两列/一个索引：
- `lastPushDate` —— 任务每小时跑，靠它保证同一天只推一次
- `idx_enabled` —— 任务每小时按 `isEnabled=1` 捞规则，必须有索引

传统节日（春节、中秋）**不进提醒**：这是修行辅助，不是节假日营销推送。

### 17.2 为什么不用本地通知

原型里写的是 WorkManager 本地调度，实际改成服务端推送，原因三条：

1. Android 12+ 精确闹钟要 `SCHEDULE_EXACT_ALARM` 权限，用户不给就只能推迟到几小时后，"提醒"失去意义
2. 国产 ROM 清后台是常态，本地任务被清掉用户根本不知道
3. 用户跨时区（留学、出差）时本地定时间戳会错位，服务端按上报时区反算则是自适应的

代价是依赖推送权限。所以设置页顶部有「通知未开启」引导条——权限没开还让用户配提醒，等于骗人。

### 17.3 服务端

| 接口 | 说明 |
|---|---|
| `GET /userTool/getRemindList` | 首次调用自动补两条默认规则（节日提醒开、斋日提醒关），客户端不用拼模板 |
| `POST /userTool/saveRemind` | id=0 新建、id>0 更新；同类型同 key 已存在时转成更新，防连点攒重复规则 |
| `POST /userTool/deleteRemind` | 只有自定义提醒给删，节日/斋日只能关 |
| `GET /userTool/getFestivalList?days=90` | 节日预告，与月历同源（`BuddhaFestivalService`） |

`CalendarRemindTask`（每小时第 4 分钟，错开早课提醒的 2 分）：按 `account_info.timeZone` 算每人本地整点 → 命中规则 → 按「标题+正文」分组批量发。一个账号一次只推一条（节日 > 斋日 > 自定义），多条规则撞在同一小时连推只会让用户关通知。

**修掉的越权点**：原 `saveRemind` 直接把客户端传的 id 塞进 `INSERT ... ON DUPLICATE KEY UPDATE`，传别人的规则 id 会改掉别人的配置；`deleteRemind` 的 `WHERE id=? AND accountId=?` 虽然拦得住删除，但删除和修改的守卫应当一致。现在两者都先校验归属。

**修掉的时区坑**：`remindTime` 改用 String 而不是 `java.util.Date`。库里是 MySQL `TIME` 列，JDBC 的 `getTimestamp` 会把它当成 1970-01-01 的 UTC 时刻再按 JVM 时区还原，小时会整体偏几个小时。字符串进出不做任何换算。

### 17.4 客户端

- 新页 `CalendarRemindFragment`（我的 → 佛历订阅提醒，原「我的足迹」坑位——足迹没有后端，换成能做实的）

- 页面底部列出「接下来的节日」（与月历同源），让用户看得见自己配的规则到底会提醒什么

## 二十一、游客登录 + 第三方绑定不换号（2026-11-03 第九批，已完成）

### 21.1 语义

游客登录 = 设备号登录：服务端按 `deviceUUID` 创建/找回游客号（`account_info` 普通行，email/googleId/appleId 全空），**享正式账号全部功能**——session、供佛、供灯、装扮、提醒一视同仁。同设备再次游客登录拿到同一个号。之后用 Google/Apple 登录时，**第三方凭证直接绑到这台设备的游客号上，账号本身不换**，游客期数据全部延续。

游客号的判定口径：`registerDeviceUUID = 本机 && isDeleted=0 && email/googleId/appleId 全空`。

### 21.2 后端

- `tryPlay` 本来就有建/找回逻辑，本轮补两处：建号落 `timeZone`（原缺失，早课/佛历推送会全按上海时区算）；复登刷 `refreshTimeZone`（与邮箱/第三方登录对齐，用户换国家后时区跟着变）。设备签名校验保留（MD5(platform+channel+version+deviceUUID+apiKey)——游客登录的凭证只有设备号，必须防伪造）
- **`loginByThird` 插入游客绑定分支**：第三方 id 查不到 → 已验证邮箱认领（原有）→ **本机游客号直接绑定（新增）** → 才轮到建新号。绑定前照常做可用性校验（封禁/注销的游客号不能被认领）；googleId/appleId 有唯一键，绑定冲突由既有 `DuplicateKeyException` 兜底
- 查询走 `idx_registerDevice` 已有索引，无 DDL

### 21.3 客户端

- 登录页恢复游客入口（`tv_guest`「游客进入」，在切换登录/注册文字与协议行之间）：不用填任何东西，点了直接 `tryPlay`
- `ApiManager` 补回 `tryPlay` 接口（海外版改造时删了）+ `NetProperty.ACCOUNT_TRY_PLAY`；`RequestBodyFactory.guestLoginBody` 一直保留着，设备签名材料齐全，直接复用
- `LoginRegisterVM.guestLogin()`：成功后与邮箱登录同一套落地（session 双写 SP/GlobalConfig、`SP_LOGIN_TYPE=0` 游客）
- 客户端无需为「绑定」做任何事：用户在登录页点 Google/Apple 时，服务端自动完成绑定

### 21.4 冒烟验证（jar 跑 8899）

首次游客登录建号（email/googleId 均 null，session 正常下发）✔ → 同设备再登同 accountId ✔ → timeZone 落库 Asia/Bangkok ✔ → 游客语义查询命中该号 ✔ → 游客 session 调登录态接口（灯状态）code=0（享正式功能）✔ → googleId 置非空后不再被判为游客（绑定后不会被第二个第三方凭证认领）✔。测试账号已清理。三端编译全过。

### 21.5 边界与注意

- 设备上有正式账号时点「游客进入」：`tryPlay` 按 deviceUUID 找回的是该设备上 accountId 最小的账号——即本机主账号。语义是「继续用这台设备的账号」，不是强制新建
- 已绑 Google 的号再登 Apple：googleId/appleId 是两个独立列，可共存（双绑定）；第三方绑定查重各自独立
- 卸载重装：deviceUUID 若变（部分设备重置广告位/应用签名），旧游客号找不回——这是设备号方案的固有边界，绑定 Google/Apple 后即不受影响

### 21.6 游客绑定引导（客户端）

设备号方案的固有风险（卸载重装找不回）要用产品手段对冲：让游客尽早绑定。两处引导，均为纯客户端改动：

- **设置页常驻行**：`fragment_setting.xml` 账号组最上方新增「游客账号 · 绑定后进度不会丢失」行（金色文字），仅游客账号可见（`GlobalConfig.isGuestAccount`），点击清栈进登录页绑 Google/Apple
- **购买前拦截弹窗**：`ShopFragment.confirmPurchase` 在拉起支付确认前判断游客，先弹「游客账号提醒」（确认=去绑定进登录页；取消=继续购买，不打断付费主流程）。花钱是绑定意愿最强的时刻，转化率最高

游客判定口径（客户端）：已登录 && `email/googleId/appleId` 全空（`GlobalConfig.isGuestAccount`），与服务端 tryPlay 语义对齐。绑定成功后任一凭证非空，两处引导自动消失。

## §27 供佛页 3D 佛像修复二批（v2.2，2026-11-03 下午）

真机反馈两个问题：①佛像朝向偏左 90°；②第 1→2 尊正常，左滑到第 3 尊闪退。

### 27.1 闪退根因（adb crash 缓冲区实锤）

```
NullPointerException: ResourceLoader.asyncUpdateLoad() on a null reference
  at Renderable.prepareForDraw(Renderable.java:324)
  at Renderer.updateInstances → Renderer.render → SceneView.doFrame
```

引擎链路（eq-renderer 移植版语义）：
- `RenderableInstance.destroy()` / `detachFromRenderer()` / `Node.setRenderable(换渲染体)` 都会调 `renderableData.dispose()`，把 ModelRenderable 的 glTF 数据连根销毁（resourceLoader=null、filamentAsset/AssetLoader 释放）
- 渲染体 registry 按 sourceUri 复用：同 URL 的 build 命中 registry 返回 `makeCopy()`，而拷贝构造**共享同一份 renderableData**
- 测试数据里 buddha 2/3/4 的 `buddha3DModuleUrl` 是同一个 `buddha_01.glb`，本地缓存文件名相同 → 同一 URI。§26 加的渲染体缓存（按佛像 id）持有共享数据的两个渲染体；滑到第 3 尊时旧节点（第 2 尊）滑出后被 destroy → 共享数据被 dispose → 第 3 尊节点下一帧渲染 → resourceLoader 已空 → NPE

结论：**这套引擎里"渲染体缓存复用"与"实例销毁"互斥**——实例销毁必然报废渲染体数据。

### 27.2 修复（WorshipFragment 重构切换模型）

- **每尊佛像一个持久节点**（`buddhaNodes: Map<Int, Node>`）：挂上场景后只挪位置、永不 destroy/detach/换渲染体；非当前佛像停放到画面外 `PARK_POSITION(50,-50,50)`（Frustum 剔除不产生绘制）
- **registryId 每次构建带随机段**（`buddha_{id}_{nanoTime}`）：彻底绕开 registry 的 makeCopy 共享——不同佛像即使 glb 文件相同也各自持有独立 glTF 数据
- **切换编排**（`showBuddhaNode`）：新节点从切换方向侧滑入（260ms 减速），旧节点反向滑出后停放；动画按节点各管各（`nodeAnimators`），快速来回切先 cancel 旧的；slideDirection=0（首次加载）直接就位
- **构建在途保护**：build 回调里若用户已切走，渲染体照常缓存、节点静默停放（相当于预加载）；仍停留在该尊才执行切换动画
- **朝向**：glb 原始朝向即正面朝相机，删掉错误的绕 Y 轴 -90° 旋转（它把佛像转成了面朝左）
- **兜底图路径**：无 3D 的佛像切过去时当前 3D 节点停放（不销毁），显示 Glide 图
- **onDestroyView**：cancel 全部动画 → destroy 全部节点实例 → 清空 renderableCache/buddhaNodes/basePositions（复用已销毁数据的渲染体会闪退；模型文件都在本地，重建代价小）

### 27.3 验证

- `:app:assembleDebug` 过；真机回归点：1→2→3→4 来回滑不闪退、佛像正面朝屏幕、滑动动画正常、切回已看过的佛像秒出（缓存命中）

### §28.1 佛龛交互简化：去选择条 + 循环滑动（v2.4，2026-11-03 傍晚）

**改动**（纯客户端，uilib）：
- `fragment_worship.xml`：删底部「佛像选择条」（左右箭头 + chips RecyclerView），底部面板直接贴底
- `WorshipFragment`：
  - 删 `initBuddhaBar`/chipAdapter 相关，`BuddhaChipAdapter.kt` + `item_buddha_chip.xml` 删除（唯一引用）
  - **修滑动失灵**：根因是 `fl_buddha_scene` 不可点击，`onTouchListener` 返回 false 导致 DOWN 不被认领、MOVE/UP 不再派发，GestureDetector 凑不齐手势。改为消费事件返回 true + `onDown=true`
  - 阈值放宽：位移 80px→60px、速度 900→600，轻滑也能切
  - **循环切换**：`(idx + delta + size) % size`，最后一尊再往左滑回第一尊，反之亦然

**真机回归点**：佛龛区域左右轻滑即可切佛、滑到头继续滑能绕回、供奉/供灯按钮不受手势影响。

### §28.2 佛龛轮播改 ViewPager2（v2.5，2026-11-03 傍晚）

**背景**：自定义 GestureDetector fling 切换是「触发式」的——判定通过才播放一段固定动画，没有手指跟手过程，观感不够丝滑。

**改动**（纯客户端，uilib）：
- `fragment_worship.xml`：佛龛区域换 `ViewPager2`（vp_buddha），`fl_scene_anim`（Lottie 预留层）叠其上但纯容器不消费点击，触摸穿透给轮播
- 新增 `BuddhaPagerAdapter` + `item_buddha_page.xml`：itemCount 放大 500 倍 + position 取模实现无限循环，初始定位中间一圈；Glide 加载 `buddhaCoverUrl`（兜底 buddhaPicture），`dontAnimate` 关掉自带 crossfade
- `WorshipFragment`：删 GestureDetector/双 ImageView 交叉淡入/属性动画整套（currentImageUrl/frontIsA/slideDirection 等字段全清）；滑动到页 = `onPageSelected` → `selectBuddha`（走持久化链路）；VM 选中（初始恢复）反同步 `setCurrentItem`，同尊互跳在回调里用 id 比对截断，不会成环
- uilib 加 `androidx.viewpager2:viewpager2:1.0.0`

**收益**：手指跟手 + 原生边缘阻尼 + fling 动量，丝滑度是系统翻页级；代码反而更少（轮播状态机全删）。

**真机回归点**：滑到最后一尊继续滑回第一尊（循环）、快速连滑不卡、恢复上次选中佛像定位正确、供奉/供灯按钮不受轮播影响。

### §28.3 循环边界衔接修复（v2.6，2026-11-03 傍晚）

**根因**：轮播滑过圈尾时 `onPageSelected` 在拖动中途触发 → `selectBuddha` → observer 用 `globalPositionOf` 反算目标页——该值恒为「中间一圈」坐标，此时轮播已在别的圈，`setCurrentItem` 瞬移打断进行中的手势。只有「最后一尊→循环后的第一尊」边界踩中，表现为衔接顿挫。

**修复**（WorshipFragment）：
- `pagerDrivenSelection` 标志位：滑动引起的选中在 `onPageSelected` 里置位（LiveData 主线程同步派发，可靠），observer 跳过 `setCurrentItem`，只更新信息头/灯状态；初始恢复/列表就绪才定位轮播
- `submitBuddhaList`：提交列表同时 Glide `preload()` 全部封面进内存缓存——循环边界页是新绑 ViewHolder，预加载后绑定即出图，不再闪空帧

**真机回归点**：圈尾往左滑与普通页间滑动手感完全一致、无瞬移/闪白；重进 App 恢复选中仍然定位正确。

### §28.4 二级页转场卡顿修复（v2.7，2026-11-03 傍晚）

**现象**：首页点签到 → 日历页，先弹加载动画、顿一下、页面才进来。

**根因**：`initShiTu` 在 Fragment 事务创建期执行，`loadCalendar`（showLoading=true）的 loading HUD 在首页上方就弹出，转场动画、新页布局初始化、HUD 同帧抢主线程 → 动画掉帧卡顿。

**修复**：视图初始化留在 `initShiTu`，带 loading 的数据请求统一挪进基类现成的 `postOnEnterAnimationEnd { }`（等入栈动画真正播完才执行，比 postDelayed 魔法数字可靠）。同模式修了四个首页入口页：
- SignInFragment：月历 + 签到信息
- EarlyPracticeFragment：修行统计
- TempleListFragment：寺庙列表（滚动加载不受影响）
- WishTreeFragment：许愿树 + 今日已许

**效果**：转场立即全速播完 → HUD 出现在新页上 → 数据回来填充。
